# 运维者手册：分阶段流转、任务预算、幂等与停止控制

本手册面向运行本仓库 dual-AI 协调流程的运维者，说明任务如何分阶段流转、每次运行如何受限、状态与事件如何保持幂等、以及在需要时如何行使操作员停止控制。本文仅作说明，不提供可直接执行的命令片段，也不构成对任何提交、审批或合并的授权。

## 1. 阶段流转

协调流程按阶段推进，任何阶段都不会自行跨越人工闸门。

### 1.1 Stage A：规划与评审

- 由规划角色把 Issue 拆解为可验证的范围、允许修改的路径和固定验证要求。
- 由评审角色依据真实证据进行审查，证据包括 PR 元数据、实际 diff、文件列表和状态检查。
- 评审结论只能是 `needs_evidence`、`changes_requested` 或 `ready_for_human`，缺失或非法结论按失败关闭处理。
- Stage A 不产生自动合并，也不产生新的后续任务。

### 1.2 Stage B：有界修复与轮次上限

- Stage B 只处理 Stage A 已明确指出的问题，修复范围限定在同一 Issue 或同一 PR 内。
- 评审轮次最多三轮；达到上限仍不满足要求时，流程停止并交由人工判断，不继续堆叠轮次。
- 修复不得引入新的范围扩张，也不得为通过审查而删除证据或绕过验证。
- 缺陷修复仅作用于同一 Issue/PR，不扩散到无关 Issue、无关 PR 或历史任务。

### 1.3 Stage C：人工合并后才选下一个任务

- 只有当前 PR 经人工审核并完成合并后，才允许选择下一个无依赖任务。
- 未合并前不得并行推进依赖该 PR 的任务，也不得提前排队后续改动。
- 合并是人工行为；任何阶段都不自动合并、不自动批准、不自动建依赖任务。
- 如果人工拒绝或长期未合并，流程保持停止，而不是另起任务维持循环。

### 1.4 不为维持循环而造任务

不得为了保持流程持续运行而创建无实际需求的 Issue、占位任务或重复任务。没有满足前置条件的真实任务时，流程应保持空闲；空闲是正常状态，不是需要被填补的故障。

## 2. 每次运行的任务预算

per-run task budget 指单次运行内允许消耗的任务额度，而不是无限续跑。

- 单次运行只推进当前已领取的任务，不追加新的任务。
- 每次运行处理的任务数量有明确上限，达到上限即结束本轮运行。
- 一次运行内不得通过拆分任务来规避上限。
- 预算耗尽后由运维者决定是否开启下一次运行，而不是由流程自行续期。
- 任务预算记录应与实际执行的任务一致，便于事后核对是否存在超预算行为。

## 3. 持久幂等与事件去重

- 运行状态需要持久化，使重复执行同一输入时得到相同结果，而不是重复产生副作用。
- 事件去重以稳定标识为准，例如 PR 的 head SHA；同一标识只处理一次，处理失败不推进去重游标。
- 去重游标只表示某次运行已完成，绝不表示批准，也不能替代人工批准。
- 重复事件、乱序事件和重放事件都应被识别并忽略，而不是重复评论、重复建分支或重复修复。
- 若标识在读取过程中发生变化，应跳过该次处理，等待稳定后再评估。

## 4. 操作员停止控制

operator stop control 是运维者在任意阶段中断流程的最终手段。

- 运维者可以随时要求停止当前运行，停止后不再启动新的阶段推进。
- 停止控制优先于任务预算与轮次上限：即使剩余预算充足，也立即生效。
- 停止后不得自动恢复；是否恢复由运维者显式决定，并重新核对证据与 head 状态。
- 停止不应通过删除状态文件、强制推送或绕过闸门来实现。
- 停止期间不创建新任务、不评论、不合并，保持工作区可审计。

## 5. 证据与裁决边界

- `needs_evidence` 表示证据不足，不视为代码缺陷。
- 遇到 `needs_evidence` 时，应先收集固定的验证证据，再重新评估，而不是直接进入修复。
- 只有确认存在真实缺陷时，才进入有界修复，且修复仅作用于同一 Issue/PR。
- `ready_for_human` 只表示可提交人工审查，不代表已批准，也不代表可以合并。
- 所有合并均需人工批准，禁止自动合并；AI 审查意见仅为建议。

## 6. 运维者检查清单

1. 确认当前阶段与当前任务，避免跨阶段并行。
2. 确认本轮任务预算尚未超限，且没有为凑数量而新增任务。
3. 确认事件去重基于稳定标识，重复事件未被重复处理。
4. 确认停止控制可用，并知道停止不会自动恢复。
5. 确认缺少证据时按 `needs_evidence` 处理，而不是当作缺陷。
6. 确认修复范围未超出同一 Issue/PR。
7. 确认合并由人工完成，且保留人工批准记录。
