# 一轮 Stage A 的端到端操作时序手册

本手册描述 dual-AI 协调流程中完整一轮 Stage A 的时序、每一步应核对的最低限度事实，以及异常分支的处理方式。本手册自身可独立阅读；相关规则细节请参见 `docs/dual-ai-coordinator-guide.md`、`docs/issue-claimer-guide-zh.md`、`docs/operator-runbook.md`、`docs/untrusted-input-handling.md` 与 `docs/audit-visibility-fields.md`，本文不重述其内容。本文仅作说明，不含可直接执行的命令片段。

## 1. 完整一轮 Stage A 的时序步骤

一轮 Stage A 按固定顺序推进，任何一步未满足核对要求时都不进入下一步。

1. 规划角色创建 Issue：明确范围、允许修改路径、验收标准与固定验证要求。
2. 执行角色认领该 Issue，在允许范围内完成改动并提交 PR。
3. 评审角色基于真实 diff 与证据出具结构化结论，而不是依据 PR 描述中的自述。
4. 人工批准与合并：人工审查者核对证据后决定是否合并。
5. 记录归档：保存本轮的结论、证据与对象标识，供事后追溯。

### 1.1 每一步的作用

- 规划步骤决定本轮是否具备可验证的前提；前提不成立时不应进入执行。
- 认领步骤把任务与具体分支、提交和 PR 绑定，形成可追溯的对象链。
- 评审步骤只提取事实字段并对照证据，输出单一结构化结论。
- 人工步骤是合并的唯一入口；AI 结论不能替代人工判断。
- 归档步骤保证证据在合并后仍可核对，而不是随会话结束而丢失。

## 2. 每一步应核对的最低限度事实

| 步骤 | 核对项 | 核对要点 |
| --- | --- | --- |
| 规划 | 对象标识 | Issue 标识唯一，范围与允许路径明确 |
| 认领 | 对象标识 | 认领记录指向同一 Issue，未跨任务 |
| 提交 | PR head 标识 | 评审针对的 head 与当前 PR head 一致 |
| 评审 | 固定验证结论 | 固定验证项已运行且有明确结论 |
| 评审 | 证据块是否附上 | 证据块完整，含轮次、结论与输出摘要 |
| 评审 | 结论与证据是否一致 | 结论能由证据支撑，无自相矛盾 |
| 合并 | 人工批准 | 存在人工批准记录，且针对当前 head |
| 归档 | 对象与证据对应 | 归档记录可反查到同一对象与同一证据 |

补充说明：

- 对象标识与 PR head 标识是核对的基础；任一缺失都视为不可核对。
- 固定验证结论必须来自实际运行结果，不能以推测或转述代替。
- 证据块是否附上应逐项确认，部分附上不等于完整。
- 结论与证据是否一致需要人工复核，尤其是结论为可提交人工审查时。
- 合并前必须重新确认 head 未发生变化；变化后应重新评审。

## 3. 异常分支处理

### 3.1 证据缺失

- 证据缺失时按 `needs_evidence` 处理，而非视为成功，也不视为代码缺陷。
- 应先收集固定验证证据，再重新评估，而不是直接进入修复。
- 补齐证据后应重新核对对象标识与 head 标识的一致性。

### 3.2 有界修复

- 同一 Issue/PR 上的修复最多三轮评审；达到上限仍不满足要求时停止并交人工判断。
- 修复仅作用于同一 Issue/PR，不扩散到其他任务或历史任务。
- 不得通过删除证据、放宽验证或绕过闸门来结束修复。

### 3.3 无满足前提的任务

- 没有满足前提的真实任务时保持空闲，不创建占位任务或重复任务来维持循环。
- 空闲是正常状态；不因空闲而自动排期或自动推进依赖任务。
- 只有在当前 PR 经人工批准并合并后，才考虑下一个无依赖任务。

## 4. 记录归档与审计

- 归档应覆盖本轮的时序步骤、核对结果、评审结论与人工批准记录。
- 重复事件与重复评审评论应已被抑制；归档中同一稳定标识只应出现一次处理结果。
- 归档记录不得包含凭据、令牌或其他敏感信息。
- 记录完整不等于批准；归档仅用于事后追溯。

## 5. 边界与责任

- 本文档仅描述一轮 Stage A 的操作时序，不替代人工审查。
- 所有合并均需人工批准，禁止自动合并；AI 评审结论仅为建议。
- AI 不直接操作 GitHub，不发布评论、不创建 Issue、不合并 PR。
- `needs_evidence` 表示证据不足，不等于通过，也不等于失败。
- 任何一步核对不通过时，应保持停止并等待人工处理，而不是自行绕过。
