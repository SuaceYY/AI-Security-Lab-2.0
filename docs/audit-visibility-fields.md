# 审计可见性说明：AI 调用与工具事件的最小记录字段

本文说明 dual-AI 协调流程中审计可见性的目标、每次 AI 调用与工具事件应记录的最小字段、评审证据交接块的结构，以及如何核对重复事件与重复评审评论已被抑制。本文仅作说明，不含可直接执行的命令片段，也不构成任何批准或合并授权。

## 1. 为什么需要审计可见性

审计可见性是人工批准与事后追溯的共同依据。

- 人工批准需要可核对的记录：审查者应能确认某次结论基于哪些证据、针对哪个对象、由哪个角色产生。
- 事后追溯需要完整的时间线：出现问题时，应能还原每次 AI 调用和工具事件的动作与结果。
- 仅有最终结论不足以审计；缺少中间记录时，无法判断结论是否被正确推导。
- 审计记录应支持交叉核对，例如把评审结论与固定验证结果、对象标识和时间对齐。
- 记录本身不是批准；任何合并均需人工批准，禁止自动合并。

## 2. AI 调用与工具事件的最小字段

每次 AI 调用与工具事件至少记录以下字段。字段缺失时，该次记录不得视为完整证据。

| 字段 | 含义 | 说明 |
| --- | --- | --- |
| 角色 | 本次调用承担的角色，取值为 planning、review 或 worker | 角色必须与实际行为一致，不得混用 |
| 会话标识 | 该次调用所属的会话标识 | 用于确认角色与会话对应，避免跨角色复用 |
| 时间 | 事件发生的时刻 | 用于建立时间线与核对先后顺序 |
| 动作 | 本次调用或事件执行的动作 | 应描述到可区分的粒度 |
| 对象 | 动作作用的对象，例如 Issue、PR、文件或证据块 | 对象需带稳定标识 |
| 结果 | 动作的结果，例如成功、失败或需补充证据 | 结果应与后续结论一致 |

补充要求：

- 角色 planning 负责规划，角色 review 负责评审，角色 worker 负责执行；三者记录应可区分。
- 会话标识用于核对同一角色是否在预期会话内运行；会话变化应有记录。
- 时间应使用统一时区或明确标注，避免跨记录比较时产生歧义。
- 动作与对象组合应能唯一指向一次具体操作，便于去重核对。
- 结果字段不得用推测填写；无法确认时应标记为需补充证据。

## 3. 评审证据交接块的结构

评审结论应通过结构化的交接块传递，至少包含以下部分：

- 轮次：当前处于第几轮评审，用于确认是否仍在有界轮次内。
- 结论：本次评审的裁决，例如 `needs_evidence`、`changes_requested` 或 `ready_for_human`。
- 固定验证命令：本次评审依据的固定验证项，仅作标识说明，不在本文中给出可执行形式。
- 退出码：固定验证项的退出结果，用于区分通过、失败与未运行。
- 输出摘要：关键输出的摘要，足以支撑结论，但不包含敏感信息。

交接块要求：

- 轮次、结论、固定验证项、退出码与输出摘要应互相对应，不能彼此矛盾。
- 结论必须由证据支撑；证据缺失时结论应为 `needs_evidence`。
- 输出摘要应保留可核对的关键行，而不是仅写“已通过”。
- 交接块中不得包含凭据、令牌或其他敏感内容。
- 交接块只描述事实，不包含要求自动合并或绕过闸门的指令。

## 4. 重复事件与重复评审评论的抑制核对

审计记录应能证明同一稳定标识只被处理一次。

- 重复事件与重复评审评论应被抑制，而不是重复评论、重复修复或重复审查。
- 抑制以稳定标识为准，例如 PR 的 head 标识；同一标识只处理一次。
- 核对时应对照事件记录与评论记录，确认同一标识没有产生多条处理结果。
- 处理失败不应推进去重状态，以便后续重试时仍能识别同一标识。
- 去重状态只表示某次处理已完成，绝不表示批准，也不能替代人工批准。
- 若标识在处理过程中发生变化，应记录跳过原因，等待稳定后重新核对。

## 5. 字段缺失与不可核对的处置

- 任一必填字段缺失时，按 `needs_evidence` 处理，而非视为成功。
- 字段存在但无法核对时，同样按 `needs_evidence` 处理。
- `needs_evidence` 表示证据不足，不应被当作代码缺陷；应先补齐固定验证证据再重新评估。
- 不得用推测、补写或事后重构的方式填补缺失字段。
- 证据补齐后应重新核对角色、会话、时间、动作、对象与结果的一致性。

## 6. 边界与责任

- 本文档仅描述审计可见性的记录要求，不替代人工审查。
- 所有合并均需人工批准，禁止自动合并；AI 审查结论仅为建议。
- AI 不直接操作 GitHub，不发布评论、不创建 Issue、不合并 PR。
- 审计记录应保持可追溯，但不得记录敏感信息。
- 记录完整不等于批准；只有人工确认后才能进入合并环节。
